# Round 30 build: release keys, chat step tabs, 4/5 props, prop anti-repeat, 30 new props (2026-11-16)

Builds the Round 30 queue (thinking/queue-next-app-round.md). Who decided: Haylee (the items, pre-approved while away); the implementation calls below are Claude's.

## 1. Release-key safety (URGENT, from the compliance research)
- `Relay.xcconfig` now holds ONLY the relay (`RELAY_HOST`, `RELAY_TOKEN`); no Secrets include.
- `Debug.xcconfig` = Relay + `#include? "Secrets.xcconfig"` (personal keys for dev, as before).
- `Release.xcconfig` = Relay + `ANTHROPIC_API_KEY =` / `OPENAI_API_KEY =` (explicitly empty; never includes Secrets).
- project.yml: Debug → Debug.xcconfig, Release → Release.xcconfig; a post-build phase "Release key check" runs `tools/check-release-keys.sh`, which fails a Release build if either key is non-empty in the built Info.plist (never prints values; Debug skipped). The built Info.plist is declared as an input so it runs after Info.plist processing.
- Verified: Release build (generic iOS Simulator) → both keys empty, relay host set, check printed "no personal keys". A fake `OPENAI_API_KEY` injected into Release.xcconfig → `error: Release key check: OPENAI_API_KEY is set…` and BUILD FAILED; reverted. Debug build still carries the personal keys.

## 2. Chat panel step tabs
- `PTChatTab` is now `step | chat`; `PTStepTab` (props, print, scene, cover) picks the step tab per phase (`PTStepTab.forPhase`): Props once a hunt card is out (first play or replay), Print once the kit papers are out, Scene in play, the cover on a replay's Pick; a first play's Pick and The End have none (The End keeps its pinned card).
- **Props | Chat:** `PTPropListPanel`: every shown prop as a row (art, name, what it becomes); the current one has a yellow ring and the big ✓ / ✗ (the same tap path as the stage card; a replay uses its replay hunt); found rows get the check badge, swapped rows the swap arrows, missing ones fade with "We'll pretend: <what it becomes>" (their pretend stand-in). Updates live. Only cards already shown are listed (one prop at a time stays).
- **Print | Chat:** `PrintTabView`: the printer (waits while the chosen set draws) and green ▶ on top, then both sets as cards (chosen = yellow ring + chip check), each a strip of 92×119 page thumbnails; a page tap chooses its set and opens the full preview.
- **Scene | Chat:** round 29's card, unchanged. **Game (cover):** the replay's cover (310 pt) and, without voice, the count tiles.
- Opening the panel always starts on the step tab (`panelOpened`); a new step or the next scene resets to it; within one step the kid's choice sticks. Tabs are 56 pt tall with an icon each (shippingbox, printer, theatre masks, photo).
- Chat open, the stage hides its duplicate: the hunt's done thumbnails (round 10's chat-open row) and the presented prop cards, a replay's cover and props. KitView already hid itself.

## 3. Props per game: 4 for 1–2 kids, 5 for 3+
- `PropLibrary.target(players:)`; `AdventureStore.propTarget`. Instructions and tool descriptions say it; every show_next_prop / mark_found / skip_prop result says "prop n of N" and, at N, "this is the LAST prop → finish_planning". A sixth show_next_prop is refused. The tap path's note and required tool follow (last prop → finish_planning only); the turn review coaches "prop n of N" and, after the last, finish_planning. Claude's tap-path prop prompt asks for exactly N.
- An early finish_planning during the hunt is held (the result asks for the next prop and her turn continues) at most twice, so a stuck model can never block the kit (Claude's call). Only the voice session turns this on (`holdsEarlyFinish`); scripted store tests are unchanged.

## 4. Prop anti-repeat
- `RecentPropMemory` (UserDefaults `pt.recentPropGames`): the PropLibrary IDs of the last 5 hunts, newest first; anything that isn't a library ID is dropped (no kid data). Recorded once per first play at finish_planning (never on a replay).
- Steering (Claude's calls): the set_roles result lists the recent IDs ("pick DIFFERENT list items this time whenever one fits"); and app-side, a recent item gives way to the model's first alternate that fits the same use, isn't recent and isn't already a card (the old item stays as the backup alternate; the tool result tells her to use the new one). No fresh fitting alternate → the item is kept (never a misfit just to be new).
